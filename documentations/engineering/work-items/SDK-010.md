## SDK-010 — Establish authoritative target identity for effectful operations

**Owner:** `CheatEngineNet/CheatEngine.SDK` · **Kind:** feature · **Priority:** P1 · **Milestone:** SDK-M2

**Initial status:** Needs refinement. **Runtime validation:** Not executed by this bootstrap.

### Context and evidence

The Client tracks an observed PID/architecture epoch, while allocation and patch bindings use CE current-target globals. This is insufficient as a universal owner-release authority.

**Evidence classification:** InheritedAuditBasis + Proposal; revalidate the pinned call path before implementation.

### Outcome and rationale

Provide SDK target observations and operation/release guards that fail safely under unobserved target changes.

**Expected benefit:** Provide SDK target observations and operation/release guards that fail safely under unobserved target changes.

### Architectural responsibility

SDK owns CE mappings, native safety, factual outcomes and low-level owners. Client owns application policy, typed workflows, composition, and developer experience.

### Technical requirements and task checklist

- [x] Distinguish target selection from process incarnation; represent unavailable identity facts honestly.
- [x] Choose explicit safe refusal for an observed original-target mismatch or unavailable identity.
- [x] Do not invisibly switch the selected process during disposal.

### Acceptance criteria

- [ ] A stale owner cannot issue cleanup against another target. The SDK refuses every mismatch it observes before the
  ambient-target call, but no inspected CE primitive binds that observation atomically to the following effect.
- [x] External A-to-B-to-A switches and PID reuse are deterministically tested; an external switch in the
  observation-to-effect interval is explicitly unsupported and not live-qualified.
- [ ] Client consumes the SDK identity without implementing another low-level authority. Adoption remains a Client
  integration task; the current Client still owns a separate selection epoch.

### Required validation

- [x] Two controlled target contexts with call counters.
- [x] Target change outside Client, process termination, same PID/new incarnation, and A-to-B-to-A return in managed
  fakes; no live Cheat Engine scenario was run.

### Maintainer notes

2026-09-21 SDK-010 implementation: `TargetSelection` models the selected PID separately from a copied local-process
incarnation (PID plus creation time). `TargetMemoryAllocator` admits an `AllocatedRegion` only through the additive
`ITargetBoundMemoryAllocationOperations` contract; legacy direct operations remain source-compatible but cannot be
silently converted into an owner with an unverified cleanup target. Allocation and Auto Assembler owners retain the
captured incarnation, refuse an already observed mismatch without calling `deAlloc`/disable or selecting a process,
and publish `TargetReleaseOutcome` for confirmed, refused, or unconfirmed release.

This is not a target lock or a live CE qualification. The inspected CE surface provides an ambient current-target Lua
effect rather than a primitive bound to an expected incarnation, so a target change after validation and before that
effect is explicitly not proven safe. `TargetSelection` and the catalog preserve that unknown; no live Cheat Engine
claim is made. The Client adoption acceptance criterion remains pending for its integration work item.

Validation on this checkout: Debug and Release solution builds completed with analyzers enabled; the Engine xUnit/MTP
executable ran 424 tests in each configuration with zero failures or skips; and
`py -3 eng\\Validate-CeSurfaceCatalog.py` passed. The repository `dotnet test --project` invocation reported zero tests
(MTP exit code 5) despite the executable discovering 424 tests, so the direct MTP executable result is the recorded
Engine test evidence. No live Cheat Engine target was started or claimed.
